# 业务规则分析

## 前置条件

本 Skill 依赖 `biz-flow` 产出的 DDD 元素分析报告。报告中必须包含:
- **实体及属性**: 含字段校验注解（Bean Validation）、set 守卫、父类字段
- **决策点清单**: 编号/所在方法/行号/决策类型/条件/动作
- **流程总览**: 调用链文本树，标注关键决策和状态变更
- **领域事件**: 事件名/触发时机/所属聚合/携带数据
- **活动列表**: 活动名/方法/所属分层/说明

## 输入

DDD 元素分析报告的**文件路径**或直接在对话中附上报告全文。

格式: `基于 <文件路径> 审查规则完整性`

---

## 核心方法论

```
SBVR 12 类规则理论框架
        │
        ▼
  对每一类规则:
  1. 理论要求: 该类规则在业务中"应该"覆盖什么
  2. 代码现状: 从实体属性、决策点、流程总览中找出"已实现"的部分
  3. 缺失识别: 理论要求有但代码中找不到 → GAP
  4. 风险定级: P0(资金/数据安全) > P1(业务逻辑) > P2(健壮性)

关键思维方式: 不是"代码中有什么规则" → 而是"理论说应该有什么规则，代码中找到了没有？"
```

## 12 类规则检查框架

| 类别 | 理论要求 | 检查点(从哪找) | 缺失判定 |
|------|---------|---------------|---------|
| 1. 校验规则 | 所有外部输入字段的类型/格式/范围/必填/组合约束 | 实体类的 Bean Validation 注解 | 字段缺注解、缺范围约束、缺格式校验 |
| 2. 存在性规则 | 跨聚合引用必须存在；有 status 字段的实体必须检查状态 | 方法中的 null 检查 + status 判断 | 查了对象但没检查 status、引用的实体可能已禁用 |
| 3. 安全规则 | 签名/加密/IP白名单/防重放/时效性 | checkParamAndGetUserPayConfig / checkIp / 签名验证 | 应有防护缺失、攻击向量未封堵 |
| 4. 不变规则 | 聚合内一致性约束、set 方法守卫、金额/数量非负 | 实体 set 方法守卫 + insert/update 配对 + 唯一性约束 | 金额变更未持久化、金额可为负、字段矛盾 |
| 5. 计算规则 | 派生字段的明确计算逻辑 | 方法源码中的计算公式、派生赋值 | 派生逻辑不明确、隐式计算无文档 |
| 6. 状态转换规则 | 每个状态转换有守卫条件；非法转换被阻止 | status 字段的 if 分支、throw 保护 | 某状态无入边/无出边、非法转换未被拦截 |
| 7. 路由规则 | 分支条件覆盖所有枚举值 | payType/payWay 等分发判断的 else/default | 某枚举值无对应分支、隐式 fallback |
| 8. 幂等规则 | 重复执行不产生副作用 | selectBy then insert 模式、状态判断 | 并发重复提交风险 |
| 9. 时间规则 | 时间格式/一致性校验、过期拦截 | orderDate/orderTime 校验、expireTime 判断 | 日期格式无校验、过期订单未拦截 |
| 10. 补偿规则 | 失败可回滚、事务原子性 | @Transactional 注解、catch 中的补偿动作 | 多条 SQL 无事务、第三方失败后状态不更新 |
| 11. 审计规则 | 关键操作记录操作人/时间/变更前后值 | LOG 语句、creater/editor 字段赋值 | 金额变更无日志、操作人未写入、错误信息泄露 |
| 12. 通知规则 | 关键事件通知外部系统 | orderSend/消息队列/回调 | 关键事件无通知 |

## 执行步骤

### 第一步: 解析 DDD 元素分析数据

从 biz-flow 产出中解析:

1. **实体属性表** → 字段名/类型/校验注解/set 守卫
2. **决策点清单** → 所有 if/throw/catch/return
3. **领域事件** → 所有已推断事件的触发时机
4. **流程总览** → 关键分支和状态变更的上下文

---

### 第二步: 逐类检查（12 类）

对每一类规则:

**2.1 列出理论要求**

1-2 句话说明该类规则在业务中的覆盖范围。

**2.2 标记已实现规则**

从实体属性/决策点/流程中提取"代码已实现"的规则，生成表格:

| # | 规则 | 实现位置 |
|---|------|----------|
| R1 | payKey @NotNull @Size(16,32) | XxxRequestBo.java |

**2.3 识别缺失 (GAP)**

每条缺失用卡片格式详细说明:

```
┌──────┬────────────────────────────────────────────────────────────────┐
│ GAPxx│ 标题 (一句话说清问题)                                            │
├──────┼────────────────────────────────────────────────────────────────┤
│ 风险 │ P0/P1/P2 — 类别                                                 │
│ 理论 │ 理论框架要求什么                                                  │
│ 现状 │ 代码现在怎么做的 (具体行号+文件名+可引用代码片段)                     │
│ 建议 │ 怎么修复                                                        │
└──────┴────────────────────────────────────────────────────────────────┘
```

**风险定级标准:**
- **P0**: 资金安全、数据一致性、可被利用的安全漏洞
- **P1**: 业务逻辑错误、状态不一致、功能缺陷
- **P2**: 健壮性、可维护性、潜在风险、用户体验

---

### 第三步: 生成缺失汇总

**按风险等级汇总:**

| 风险 | 数量 | 编号 |
|------|------|------|
| P0 — 资金安全/数据一致性 | N | GAPx, GAPy, ... |
| P1 — 业务逻辑 | N | GAPx, GAPy, ... |
| P2 — 健壮性 | N | GAPx, GAPy, ... |

**按规则类别汇总:**

| 规则类别 | 已实现 | 缺失 | 缺失率 |
|----------|--------|------|--------|
| 1. 校验规则 | N | N | % |
| 2. 存在性规则 | N | N | % |
| ... | ... | ... | ... |
| 合计 | N | N | % |

**Top 5 优先修复:**

| 优先级 | 编号 | 问题 | 影响 |
|--------|------|------|------|
| 1 | GAPx | ... | ... |
| ... | ... | ... | ... |

---

### 第四步: 量化报告

```markdown
## 规则覆盖度量

综合完整性评分:

| 指标 | 值 | 说明 |
|------|-----|------|
| DPC (决策点覆盖率) | N/N (%) | 所有 if/throw 分支的规则发现率 |
| APC (属性约束覆盖率) | N/N (%) | 实体属性中被校验注解覆盖的比例 |
| ERC (事件-规则完备) | N/N (%) | 领域事件中有对应触发规则的比例 |
| STC (状态转换覆盖率) | N/N (%) | 状态值中被覆盖的跃迁比例 |
| 规则发现率 | N/N (%) | 已发现规则 / 推测完整规则空间 |

规则发现总数: 已发现 N 条规则 (已实现 N + 缺失 N)
猜测完整规则空间: ~N 条
当前提取率: N/N = XX%
```

## 执行约束

- ⚠️ 只读分析，不修改任何代码
- ⚠️ 每条 GAP 必须有具体证据: 文件名 + 行号 + 代码片段
- ⚠️ 每类规则必须检查，不能跳过。如果该类无缺失，标注"=== 缺失场景: 无 ==="
- ⚠️ P0 级别的 GAP 必须优先排列，涉及资金的必须有明确的风险描述
- ⚠️ 不确定的推断标注"推测"而非断言
- ⚠️ 已实现规则写简称即可，缺失规则 (GAP) 必须写详细卡片
