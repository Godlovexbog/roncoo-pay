## 需求影响分析

基于已沉淀的全局知识 + GitNexus 实时事实，对需求做澄清和多维影响分析。

**前置条件**: `docs/biz-loop/panorama/` 已就绪
**产出**: `docs/biz-loop/requirements/<YYYY-MM-DD>-<需求简称>/`

### 命令

| 命令 | 说明 |
|------|------|
| `/biz-impact <需求描述>` | 完整流程：澄清 → 影响分析 → 测试案例 |
| `/biz-impact clarify <需求描述>` | 仅需求澄清 |
| `/biz-impact analyze <需求目录>` | 基于已有澄清文档跑影响分析 + 测试案例 |
| `/biz-impact quick <需求描述>` | 跳过澄清，直接出简化影响报告(不含测试案例) |

---

### Phase 1: 需求澄清 (full/clarify 模式)

读全景知识 + 需求描述，按 6 个维度写澄清文档 `docs/biz-loop/requirements/<date>-<name>/1-clarification.md`：

1. 先读 `docs/biz-loop/panorama/` 下所有 .md 文件 + CLAUDE.md
2. 按以下维度写文档：

**业务目标** — 一句话说清要达成什么业务目的

**用户场景** — 典型使用场景 + 当前痛点。如果 flow-maps.md 包含相关流程，链接过去

**接口契约** — 对齐 api-list.md 风格，表格：方法/路径/入参(字段+类型+必填+说明)/返回(字段+类型+说明)/错误码

**边界场景** — 至少 8 条，每条标 `[预期行为]` 或 `[待产品决策]`。从现有代码反推优先

**老项目约束** — 从 CLAUDE.md 禁区+历史包袱提取相关条目，从 config.md 提取限制，每条标注来源

**不在范围里的事** — 候选清单，标"本期不做"或"留到下期"

完成后**暂停，等待用户确认**。确认后将[待产品决策]条目替换为确认结果。

### Phase 2: 多维影响分析 (full/analyze/quick 模式)

**2.1 确定可用维度**

读 `docs/biz-loop/panorama/` 下文件列表，确认实际存在哪些维度的知识文件。

**2.2 代码链路影响**（始终运行）

从需求提取关键词 → `query({query: "<关键词>"})` 定位核心符号 → `impact({direction: "upstream"})` 获取调用者和受影响 Process → 如有 API 变更则 `api_impact()` + `shape_check()`

**2.3 全景知识影响**（按实际存在的维度顺序分析）

> ⚠️ **关键**: 全景知识文件有层次 — 顶层文件(如 rules/INDEX.md)只含元数据，真正的细节在子目录(如 rules/methods/)。必须深入读取细节文件才能产出有行号、有具体行为的变更描述。

对每个维度，**按以下步骤**提取细节（不可只回答"是/否"，必须产出结构化清单）：

**a) 数据模型 (data-model.md) — 产出: 每个受影响 Entity 的全字段变更表**
- 读 data-model.md → 找出与需求相关的 Entity
- 对每个受影响的 Entity列出**全部字段**（含基类字段），标注每个字段的变更类型: ➕新增 / ✏️修改 / ➖删除 / 🟢不变
- 新增 Entity: 逐字段列出（字段名/类型/说明）
- 修改 Entity: 原字段语义 → 新字段语义
- 如 Entity 有扩展字段(如 field1-5)，评估复用可行性并标注判断前缀

**b) API 接口 (api-list.md) — 产出: 每个受影响端点的参数变更表**
- 读 api-list.md → 找出与需求相关的端点
- 对每个端点标注: 新增/修改/不变
- **新增端点**: 完整列出 方法/路径/入参(字段+类型+必填+说明)/返回(字段+类型+说明)/错误码
- **修改端点**: 标注新增参数/修改参数/删除参数，以及消费者影响（谁在调用这个接口）
- 管理后台接口（boss/merchant）同样列出受影响的列表查询/详情接口

**c) 业务规则 (rules/INDEX.md + rules/methods/) — 最高价值维度，产出: 逐条规则的当前→目标变更表**
- 读 rules/INDEX.md → 找出与需求关键词匹配的方法文件
- **必须**读取匹配的方法规则文件（`rules/methods/**/xxx.md`），**不可**只读 INDEX
- 每个方法规则文件包含: 源码位置+行号、决策点→规则(条件+规则描述+规则类型)、数据流(读/写表+外部调用)
- 基于具体规则，逐条判断: 不变/修改(当前行为→目标行为)/新增
- 按规则类型（校验/路由/状态机/资金/策略）分组，每个组展开为子节
- **每个受影响的源方法必须独立成子节**，列出该方法的每条规则ID+行号+条件+当前行为→目标行为
- 最后列出不受影响的规则范围（类名+方法名+规则数）

**d) 流程 (flow-maps.md) — 产出: 每个受影响流程的步骤级变更**
- 读 flow-maps.md → 找出相关流程
- 对每个流程标注: 受影响步骤数 / 新增步骤类型及数量（入口/决策/计算/DB/外部调用/MQ） / 关键风险
- 引用 flow-maps.md 的节号（如 §2.1）
- 如果某个步骤的调用链发生变化，展开描述

**e) 配置 (config.md) — 产出: 每个新增/修改配置项的完整说明**
- 读 config.md → 找出与需求相关的配置项
- 每个新增配置项: 配置项名 / 所属文件 / 默认值 / 说明 / 加载方式（对应 config.md 四种模式之一）
- 每个修改配置项: 原值 → 新值 / 修改原因
- 标注配置加载方式（Spring Boot自动 / @PropertySource / 静态块 / @Configuration硬编码）

**f) 外部依赖 (external-deps.md) — 产出: 每个受影响依赖的逐项检查**
- 读 external-deps.md → 逐一检查: 支付通道API / 中间件 / MQ队列 / HTTP客户端
- 每个受影响项标注: 当前行为 / 变更后行为 / 风险
- MQ 队列: 标注生产者/消费者/消息格式变化

**g) 架构 (architecture.md) — 产出: 10模块影响矩阵表**
- 读 architecture.md → 对每个模块标注: 影响级别(🔴HIGH/🟡MEDIUM/🟢LOW) + 变更内容摘要
- 不可只列模块名

**2.4 合并输出** `2-impact-report.md`：按以下结构输出。

> ⛔ **细节红线（所有节必须遵守）**: 
> 1. 每个变更点必须定位到**文件路径+行号**（从 rules/methods/ 或源码阅读获取）
> 2. 每条规则变更必须包含**当前行为→目标行为**（不能只写"修改"二字）
> 3. 汇总表可以存在，但**后面必须跟逐条详情**（不能只有汇总数字）
> 4. §6 业务规则是最高价值节，**每个受影响的源方法必须展开为子节**，逐条列出规则ID+当前→目标
> 5. 如果某个节产出只有汇总数字没有逐条详情，**视为不合格**

**报告结构**：

### Phase 3: 测试影响与验证案例 (full/analyze 模式)

> quick 模式跳过此阶段

**3.1 场景建模 —— C-E-A-R 四元组**

对每条受影响入口链路，用 **C-E-A-R 模型** 结构化描述场景，确保可追溯：

```
C  (Command)   谁/什么触发 — API请求 / 外部回调 / 定时任务 / 用户操作
E1 (Entity)    涉及哪些数据 — 输入 Entity / 输出 VO / 持久化 Entity
A  (Activity)  执行哪些活动 — 调用链: Controller → Service → DAO → 外部调用
R  (Rule)      受哪些规则约束 — 校验规则 / 路由规则 / 状态机规则 / 资金规则
E2 (Event)     产生什么结果 — 状态变更 / 数据写入 / 通知 / 拒绝返回
```

每个场景标注完整度: C✓ | E1✓ | A✓ | R✓ | E2✓ = N/5

**场景分类与推导规则**：
- ✅ 正常场景 — 所有 R 通过, routing 走正常分支
- ⚠️ 异常场景 — 至少一条 R 不满足, 或 external 调用失败
- 🔒 安全场景 — 签名/权限/幂等 rule 被绕过
- 🔄 兼容场景 — 已有调用方不受影响

**3.2 识别受影响入口链路**

对 Phase 2.2 中每个受影响的入口 API，用 GitNexus context 追踪完整调用栈：

```

      ├── CnpPayService.checkParamAndGetUserPayConfig  [校验]
      ├── RpTradePaymentManagerServiceImpl.initDirectScanPay  [核心, 🔴 变更]
      │   ├── RpTradePaymentOrderDao.insert              [DB]
      │   ├── RpTradePaymentRecordDao.insert             [DB]
      │   └── RpPayWayService.getByPayWayTypeCode         [费率]
      └── getScanPayResultVo                              [渠道, 🔴 变更]
          ├── WeiXinPayUtils.httpXmlRequest               [外部调用]
          └── RpNotifyService.orderSend                   [MQ]
```

每条链路标注：
- 哪些节点**不变**(🟢)、**修改**(🟡)、**新增**(🔴)
- 对应的 flow-maps.md 流程名称和步骤号

### Phase 4: 决策记录 + 风险分类

提取澄清文档的[待产品决策] + 影响报告中 🔴 高风险项 → `4-decision-log.md`。

**输出内容**:
1. **需求澄清决策**（Phase 1 确认的 [待产品决策]，含结果+理由）
2. **影响分析高风险项**（Phase 2 发现的 🔴 项，含缓解措施+验证方式+状态）
3. **实施顺序建议**（Phase 1→N，每Phase含依赖+文件数+预估工时）
4. **未决事项**（仍待外部确认的问题）

**风险分类原则** — 在决策记录中区分两类：

### 关键原则

- **细节红线（最高优先级）**：§6 业务规则禁止只有汇总数字，必须深入 `rules/methods/` 读取具体规则文件，逐条列出规则ID+源方法+行号+当前行为→目标行为。任何节如果只有汇总表没有逐条详情，视为不合格。
- **全景知识有层次**：INDEX.md 只含元数据，真正的细节在子目录（`rules/methods/` 下有108个方法规则文件，每个含决策点+行号+数据流）。不可只读顶层文件。
- **按需不铺开**：四维分析矩阵(功能/性能/安全/兼容)是内部检查清单，只在检测到触发条件时才向用户展开对应子维度
- **变更点必须定位到行号**：每个变更点包含文件路径 + 行号（从 rules/methods/ 或源码阅读获取），让开发可以"按图索骥"
- **逐项确认不跳过**：澄清阶段每个[待产品决策]必须等用户确认后才能继续
- **风险必须分级**：🔴高（阻塞/资金安全）/ 🟡中（逻辑变更/兼容）/ 🟢低（展示层），并区分"变更风险"和"现有技术债"
- **影响链路必须可视化**：以入口方法为根的调用树，每层标注影响类型（🔴新增/🟡修改/🟢不受影响/⚡需扩展）
- **实施顺序按依赖排列**：枚举层 → Entity/DAO → Service → Controller → 视图层 → 配置/测试
- **场景可执行**：每个场景必须描述清晰的触发条件和预期结果（含 curl 命令）
- **不猜测不编造**：所有分析基于全景图 + GitNexus 实时数据 + rules/methods/ 具体规则文件，不做无根据推断
- **重构建议标注"非本次必须"**：识别长期改进机会但避免范围蔓延
